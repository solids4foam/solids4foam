# solids4foam repository guide

This guide is for agents that write or review changes in solids4foam. The
rules in sections 1-5 apply to both. When reviewing, use them as review
criteria; section 6 applies only when making changes.

## 1) Compatibility, numerics and known pitfalls

- The supported releases are those accepted by the top-level `Allwmake`
  (OpenFOAM.com, OpenFOAM.org and foam-extend). Variant code is selected with
  `OPENFOAM_NOT_EXTEND`, `OPENFOAM_COM`, `OPENFOAM_ORG` and `FOAMEXTEND`. A
  change to a guarded block usually needs a matching change in the other
  branches.
- In `src/solids4FoamModels` and `src/blockCoupledSolids4FoamTools`, sources
  go in `Make/files.openfoam` (OpenFOAM.com and .org) and/or
  `Make/files.foamextend`, for the variants they support; `Make/files` there
  is generated by `Allwmake`. Elsewhere, edit the tracked `Make/files`.
- `triangle::normal()` is the area-weighted normal in OpenFOAM.com and
  foam-extend but the unit normal in OpenFOAM.org. Use `triangleAreaNormal()`
  (`numerics/amiZoneInterpolation/triangleWeights.H`).
- Do not pass an unnamed `tmp` operand whose type equals the result type to a
  field product such as `nf() & (-devReff().boundaryField())`. OpenFOAM may
  reuse its storage for the result while the `__restrict__` loop still reads
  it, which gives wrong results with some GCC `-O3` builds. Materialise the
  operand as a concrete field, e.g. `const vectorField nf(patch.nf());`;
  naming a `tmp` is not enough (see `applications/test/tmpAliasProducts`).
- `solids4FoamModels` supports unity builds (`S4F_UNITY_BUILD=1`), which
  compile several `.C` files as one translation unit. `#undef` macros defined
  in a `.C` file at its end and avoid file-scope names that could clash;
  otherwise list the file in `Make/unity-exclude`.
- Parallel: reduce processor-local contributions (`gSum`, `gMax`, `reduce`)
  when computing global quantities, but do not reduce data that is already
  global on every processor, such as FSI interface zone fields. All ranks must
  call collectives in the same order and number, so never reduce inside
  per-cell or per-law callbacks. Consider processor and other coupled patches.
- A new dictionary entry needs a default that leaves existing cases
  unchanged, unless the change is intended and documented. New state fields
  must be written and read back exactly on restart.
- Preserve dimensions, stress and configuration measures (finite-strain laws
  return Cauchy stress), interface traction signs, mapping direction, and
  displacement and time-level conventions.
- A change to a residual must keep its Jacobian consistent, or state that the
  Jacobian is an intentional approximation; several solvers use approximate
  Jacobians by design.

## 2) Architecture

- `solids4Foam` (`applications/solvers/solids4Foam`) is a thin front end. The
  `type` in `constant/physicsProperties` selects a `solidModel`
  (`solidProperties`), `fluidModel` (`fluidProperties`) or
  `fluidSolidInterface` (`fsiProperties`). An FSI interface owns one fluid and
  one solid model, whose dictionaries are in `constant/solid` and
  `constant/fluid`, and implements the partitioned coupling.
- Runtime-selectable classes need `TypeName("...")` in the header,
  `defineTypeNameAndDebug` and `addToRunTimeSelectionTable(...)` in the source
  (or the established equivalent macro), and the source in the build list. The
  selection keyword's value (`type`, `solidModel`, `fluidModel`,
  `fluidSolidInterface`, ...) must match `TypeName` exactly.
- Mechanical behaviour comes from the `mechanicalConstitutiveLaw` framework
  (`src/solids4FoamModels/mechanicalConstitutiveLaw`, design in its
  `README.md`):
  - laws are stateless functions of kinematics and state; history lives in
    `mechanicalConstitutiveLawState`, owned by
    `mechanicalConstitutiveLawManager`, which also commits it at the end of a
    step;
  - a law reads committed history through the old-time `get...0` accessors
    and writes current state; using a creating accessor to read silently
    gives zero history;
  - a tangent query must not disturb state; the solid model owns its
    implicit stiffness (`impK`) and tangent storage;
  - the manager must not depend on `solidModel`;
  - restart data is the exact integration-point state; projected output
    fields are not restart state;
  - a law class is named `<type>MechanicalConstitutiveLaw` in its own
    directory under `mechanicalConstitutiveLaws/` with a `README.md`, listed
    in `src/solids4FoamModels/materialModels/README.md`, and needs an entry in
    `applications/test/mechanicalConstitutiveLawChecks/case/constant/lawChecks`
    (the test fails otherwise).
- `constant/mechanicalProperties`: `mechanical` is a list and `planeStress` is
  top-level. With more than one material, each entry name is a cellZone, the
  zones cover every cell exactly once, and the cell-centred models need
  `leastSquaresS4f` for the displacement gradient. Do not bypass the guards
  that refuse unsupported multi-material or topology combinations.
- Thermal properties come separately from `materialModels/thermalModel`
  (`constant/thermalProperties`, `thermalLaw`). The density used by the heat
  equation comes from the mechanical model.

## 3) C++ style

- Added and changed C++ lines must follow the OpenFOAM Coding Style Guide
  (<https://openfoam.org/dev/coding-style-guide>). This is enforced: a style
  violation in changed code is a blocking review finding. Much existing code
  does not fully conform; do not reformat lines the change does not touch.
  Key rules:
  - at most 80 characters per line; indent 4 spaces, never tabs; no trailing
    whitespace;
  - braces on their own lines, and always around control-statement bodies
    (except a lone `break` or `continue`); `if (`, `for (` and `while (` take
    a space, `forAll(` does not;
  - spaces around `+`, `-`, `&`, `^`, `=`, `==`, `!=`, `<`, `>`, `<=`, `>=`,
    `||` and `&&`; none around `*` and `/` (`a*b`, `a/b`);
  - split long lines after the return type (function name left-aligned on
    the next line) or after `=` (continuation indented 4 spaces), with
    operators at the start of continuation lines; put a long argument list
    one argument per line inside parentheses on their own lines;
  - stream output as `Info<< "..."`, with continuation `<<` aligned four
    characters after the start of the stream name;
  - pass `bool`, `label`, `scalar` and other primitives by value and larger
    types by reference; use `const` wherever it applies; initialise const
    references with `=`; prefer `++iter`;
  - British spelling in comments and text (`neighbour`), `-ize` in
    identifiers (`initialize`).
- solids4foam conventions on top of the guide: `.C` files usually open
  `namespace Foam` and the model-family namespace rather than fully scoping
  every name; follow the neighbouring file. Otherwise follow the surrounding
  code for naming and include order.
- Keep the standard structural comments: section separators such as
  `// * * * Constructors * * * //`, class declaration banners, namespace and
  end-of-file banners, and `//-` documentation comments on declarations. For a
  new `.H`/`.C` pair, copy the layout of the closest class in the same model
  family. Add a section banner only when the section exists.
- In `.H` files separate member function declarations with one blank line; in
  `.C` files separate function definitions with two.
- Prefer explicit, readable, local code over clever expressions or
  abstraction-heavy rewrites.
- Comment only non-obvious behaviour; do not add redundant comments.
- New C++ files use the solids4foam licence block ("This file is part of
  solids4foam"), not the OpenFOAM one. CI runs
  `applications/scripts/solids4FoamChangeCopyright.sh`, which rewrites
  headers in place, on changed `.C`/`.H` files. `optionalFixes/` holds
  upstream copies that keep their original headers. Do not change existing
  copyright headers unless asked.

## 4) Cases, tutorials, tests and scripts

- Case dictionaries use the solids4foam banner with `Version:`, `Web:` and
  `Disclaimer:` lines. `Version:` must be the latest released `## [vX.Y]`
  heading in `CHANGELOG.md`, not a value copied from an old file.
- Write each patch entry in expanded multi-line form, one keyword per line;
  never `frontAndBack {type empty;}`. In `blockMeshDict`, put each vertex and
  each face on its own line.
- Every tutorial case with an `Allrun` needs a `README.md` (CI checks this).
  Copy the layout of a neighbouring tutorial README: optional `sort:` front
  matter, a title ending with the case name in backticks, `Prepared by
  <authors>`, then sections such as `## Tutorial Aims`, `## Case Overview`,
  `## Running the Case`, `## Expected Results` and optionally
  `## Verification and Convergence Study` and `## References`, separated by
  `---`. Do not add a "where to find the case" line.
- Cases should have a `regressionTest.sh` (CI warns if missing), and it must
  be listed in `tutorials/Alltest-regression`; regressions are not discovered
  automatically. `Alltest` is a smoke test and does not check numerical
  results. Numerical changes need reference values and tolerances, and
  skipped checks must be reported as skipped, not passed.
- Use one regression reference and tolerance for all OpenFOAM and foam-extend
  variants. Variant-specific values are an exception: give them only with a
  comment explaining the cause and size of the difference, and open a GitHub
  issue when the cause is not understood or may be a defect. Do not widen a
  tolerance just to make variants agree without the same justification.
  Select variants with `solids4Foam::foamFlavour`.
- Use the helpers in `applications/scripts/solids4FoamScripts.sh`, for
  example `solids4Foam::caseDoesNotRunWithFoamExtend` and
  `solids4Foam::requirePetscOrExitSilently`, and match the existing
  `Allrun`/`Allclean` style.
- Use bash and standard Unix tools for orchestration and regression
  infrastructure: `Allrun`, `Allclean`, `regressionTest.sh`,
  `regressionTests/` and `Alltest`.
- Python is acceptable where OpenFOAM utilities cannot do the job or would be
  much messier, such as geometry, STL or `blockMeshDict` generation, setting
  initial fields, analytical solutions and post-processing, and in opt-in
  `verification/` and `validation/` scripts (`Allverify`, `Allvalidate`).
  Keep dependencies minimal:
  - anything run by default from `Allrun` uses `python3` with the standard
    library only, and checks that `python3` is available;
  - `numpy`, `scipy` and `matplotlib` are acceptable in opt-in verification,
    validation, analytical and plotting scripts; optional plotting may skip
    when a module is missing, but required calculations must fail clearly;
  - avoid other third-party modules; document any justified exception.
- Markdown must pass `markdownlint` and should be concise and
  repository-specific.
- Record significant user-facing changes under `## [Unreleased]` in
  `CHANGELOG.md`.

## 5) Scope of changes

- Make the smallest correct change; preserve existing architecture, naming
  and dictionary-driven configurability.
- Every changed line should trace to the request, a required build fix, or a
  test or documentation update for it. Do not reformat, rename or clean up
  unrelated code; mention it separately instead.
- Do not add dictionary options, switches, fallbacks or dependencies unless
  required.
- Behaviour changes must be stated, not silent.
- Split unrelated concerns into separate commits or pull requests.

## 6) Working on a change

- State assumptions when the target variant, intended behaviour or expected
  numerical result is unclear. If several interpretations are plausible, ask
  or present the trade-off; push back on unnecessary redesign.
- Read nearby code first and follow its patterns. When adding a class, update
  registration, build lists, tests and documentation.
- Verify with the narrowest relevant build, test or case, and report what was
  and was not verified. Pull requests target `development`.

Common reference files: `src/solids4FoamModels/README.md` (library layout,
build lists, unity builds), `src/solids4FoamModels/materialModels/README.md`,
`src/solids4FoamModels/mechanicalConstitutiveLaw/README.md`, and the base
classes `physicsModel.H`, `solidModel.H`, `fluidModel.H` and
`fluidSolidInterface.H` under `src/solids4FoamModels`.
